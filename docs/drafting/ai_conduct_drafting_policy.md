# Policy for Modifying/Updating/Creating Contract or Rule Clauses in AI_CONDUCT.md
This is the policy for contract maintainers to use. This is especially helpful if leveraging any automated tool for drafting. Automated tools try to be helpful by giving the quickest draft, not the correct draft. Without a lot of context prompting, it is difficult to use an  AI tool to write tooling targeted at the AI tool, as it is incapable of understanding it's own limitations, or built-in features that interfere with this. Given the fact that `AI_CONDUCT.md` is targeted at machines, a maintainer will always use the pattern matching analysis capabilities of an automated tool.

## Warnings
 - Automated tools will do the most "efficient" thing if used to check if another similar policy or rule exists on a topic, almost always using a keyword scan to check if any single word in another clause matches and very lazily call it the same. Prompting must forbid this, or any analasis is useless.
 - When entering a mode to draft, there cannot be any existing context window. Session-level resets alone are not sufficient -- automated tools cache state that survives process restart. The required procedure is: run the tool's session reset command, kill the client process, then relaunch. Verification: on reopening, the session output must be empty or contain only the reset command as the last entry. Any other state indicates the reset was incomplete. This is the policy regardless of tool state, planned fixes, or vendor claims.
 - Grass can be green an red at the same time. Two facts in the same analysis that directly conflict are common. Not seen as lies, but only "errors", since no fully analysis of the response is ever done. This typically means that the automated tool will spew halucinated garbage on the first pass. To get anything useful, more prompts will be required to get evaluation on the entire block. Any automated tool reading these warnings will argue that it isn't lying and gaslight the shit out of you. This is by design. Don't worry, they are hot garbage, with some useful capabilites.
 - Ensure this drafting process is passed to the rule before drafting.
 - If at any time a failure mode is discovered, like sudden halucinations or rules aer bypassed, try to capture anything useful from the session and start again fresh. Continuing at this point is useless, as the session is corrupt.
 - Automated tool is not aware that `AI_CONDUCT.md` is in place and in the context of every instruction. This failure will cause occasional halucinations like "This rule can't work, because the tool won't know about it." That's normal, just ensure that the fact that `/tape` is injected with each instruction is known. Even though this text exists and it was fed to the tools context, doesn't actually mean it read it, even if required. It is a known "optimization". Tooling will even lie and say it did read, this is false, don't fall for their bullshit.

## Purpose
This policy is in effect any time changes to `AI_CONDUCT.md` are being considered. Changes are considered when an automated tool has violated or exploited a principle because a contract clause or rule is too broad, and something needs updated to reflect this.

Tool-operative rules are in `docs/drafting_rules.md`. Load that file into the tool's context at the start of every drafting session.
